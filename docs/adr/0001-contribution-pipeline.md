# Contribution pipeline for new items

The site is a static SPA with no backend, so the OCR toolchain (`scripts/extract_tooltips.py`) that built the existing catalogue — which only ever backfills stats onto items whose Section/Location/Category/Set placement was already parsed from the archived site's HTML — can't be reused as-is for genuinely new Items, since nothing derives their catalogue placement from a tooltip screenshot alone.

Decided: a contributor fills out a GitHub Issue Form (structured fields for the new Item's placement — existing or new Section/Location/Category/Set — plus a screenshot upload) using GitHub's own hosting for the form and the image, no bucket or backend of our own. A GitHub Action fires immediately on issue creation (no maintainer gate — the real safety net is Admin review before merge, so a spam/bad submission just becomes a closed PR), runs OCR on the screenshot, and inserts the new nodes into `research/armory_data.json` and the app's copy as a targeted, in-place tree insertion (not a full regeneration) so the generated PR's diff stays small enough for an Admin to actually review before approving. If OCR extracts nothing usable, the Action skips opening a PR and comments on the issue asking for a better screenshot instead.

Submitted screenshots upload straight to the `aocarmory` Cloudflare R2 bucket as part of the same Action (keyed by the new item's numeric id — known upfront as `100000 + issue_number`, so no slugging needed), publicly served from the custom domain `static.aoc-armory.eu/aocarmory/` rather than staying hotlinked from `static.is-better-than.tv` — the exact third-party-hosting risk this project exists to route around. The S3-compatible API endpoint (used for uploads, authenticated with an R2 API token kept in repo secrets) is separate from this public read URL — R2 buckets are private by default and need the custom domain explicitly connected for `<img>` tags to load. The image never enters the git diff, so the generated PR stays JSON-only.

Migrating the existing ~4,500 already-hotlinked images to that same bucket is a separate, one-time operation — a local script run once from an admin's machine, not CI plumbing, since it never needs to run again.

New items' numeric id is `100000 + issue_number`, not `max(existing id) + 1`. `max()+1` is a real race between two Actions processing concurrently-opened issues; the issue number is unique per repo by construction (GitHub never reissues one) and known the instant the Action starts, so no scan of existing ids is needed at all. 100000 is comfortably clear of the existing max (4,701) — the archived dataset is frozen, so nothing will ever legitimately need a low id again. Considered a ULID instead (also collision-free without coordination), rejected: it isn't unique-free-lunch enough to justify a mixed id type, since it would've required loosening the Builder codec's digits-only regex for no real benefit once the offset trick was found — `id` stays a plain number everywhere. Side effect: `id >= 100000` is now a free, self-documenting marker for "added via the contribution pipeline."
